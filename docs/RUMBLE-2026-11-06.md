# 震动回传实现与验证（2026-11-06）

## 1. 背景

`desktop/vendor/vigem_native.py` 是 v1.1.0 为摆脱 pip `vgamepad` 依赖而自研的
ViGEmBus 协议级客户端。它在功能上替代了 `vgamepad.VX360Gamepad`，但
`register_notification` 一直是个桩：

```python
def register_notification(self, fn) -> None:
    raise NotImplementedError("vibration feedback pending")
```

结果是接收端每次创建设备都打一条告警：

```
1P 力反馈回调注册失败（震动回传不可用）：vibration feedback pending
```

早期版本（v1.0.1–v1.0.10）使用 pip `vgamepad`，其 `VX360Gamepad` 原生支持
力反馈，因此「震动回传」属于**功能倒退**，本次补齐。

## 2. 链路结构（本次只缺中间一段）

| 环节 | 状态 |
|---|---|
| 手机端接收 `VGPR` | **早已实现**：`UdpSender.rumbleLoop()` 绑定 26761，校验 8 字节定长与 `56 47 50 52` + version=1 |
| 手机端振动 | **早已实现**：`MainActivity.handleRumble()`，含强度增益、时长、最小间隔三项设置 |
| PC 端组包发送 | **早已实现**：`receiver._make_pad()` 内 `on_feedback` → `sock.sendto(b"VGPR" + ...)` |
| PC 端注册驱动回调 | **缺失** → 本次实现 |

即：协议（`docs/PROTOCOL.md` §1.3）与两端管线都已就绪，只差驱动层的挂起请求。

## 3. 驱动层实现

### 3.1 协议依据

来自 ViGEmBus `v1.17.333.0` 的 `sdk/include/ViGEm/km/BusShared.h`：

```c
#define IOCTL_XUSB_REQUEST_NOTIFICATION BUSENUM_RW_IOCTL(IOCTL_VIGEM_BASE + 0x200)
// BUSENUM_RW_IOCTL = FILE_WRITE_DATA | FILE_READ_DATA  →  CTL_CODE 访问位 = 3
// 结果：0x002AE804

typedef struct _XUSB_REQUEST_NOTIFICATION {
    ULONG Size;        // sizeof(this)
    ULONG SerialNo;    // 目标设备序列号
    UCHAR LargeMotor;  // 大马达 0-255
    UCHAR SmallMotor;  // 小马达 0-255
    UCHAR LedNumber;   // XUSB.sys 分配的槽位/LED
} XUSB_REQUEST_NOTIFICATION;   // sizeof = 12
```

语义与官方 `ViGEmClient.cpp:vigm_target_x360_register_notification` 一致：
对总线设备反复投递**挂起** IOCTL，驱动在游戏下发震动时完成请求，
随后立即重新投递，形成长驻监听。

### 3.2 关键陷阱：句柄不能复用

第一版直接复用提交报文的主句柄（`self._client`），实测出现**致命阻塞**：

```
阶段1（未注册）update 次数=514  最大=0.15ms
阶段2（已注册）update 次数=1    最大=∞（永久阻塞）
```

原因：`_open_bus()` 以 `FILE_ATTRIBUTE_NORMAL` 打开，是**同步句柄**。
在同步句柄上投递 overlapped 请求后，该句柄被这个挂起请求独占，
后续 `IOCTL_XUSB_SUBMIT_REPORT`（报文提交）全部排队死等。

表现在用户侧就是：手机连上后几秒内还能动，随后**输入完全卡住**，
界面显示「连接中断，正在自动重连…」——因为接收端主线程阻塞在 `update()`，
不再回 `VGPP`，手机端判定链路中断。

修复：力反馈使用**独立的重叠句柄**：

```python
FILE_FLAG_OVERLAPPED = 0x40000000
flags = FILE_ATTRIBUTE_NORMAL | (FILE_FLAG_OVERLAPPED if overlapped else 0)
self._notif_handle = _open_bus(overlapped=True)
```

修复后同一测试：

```
阶段2（已注册）update 次数=860  最大=0.20ms  均值=0.04ms   回调事件=6
```

### 3.3 回调线程

- 独立 daemon 线程，200 ms 轮询 `WaitForSingleObject`，兼顾及时性与可打断；
- 回调签名与 `vgamepad` 对齐：`fn(client, target, large, small, led, user_data)`，
  故 `receiver.py` 的 `on_feedback(client, target, large, small, led, user_data)`
  无需改动；
- 回调内部异常被吞掉，不中断监听；
- `unregister_notification()` 置停止标志 → `CancelIoEx` 取消挂起请求 →
  等待线程退出 → 关闭专用句柄，无句柄泄漏。

## 4. 验证

### 4.1 驱动级（不接手机）

自建虚拟手柄 + `XInputSetState` 模拟游戏下发：

| 下发 (left,right) | 期望 (large,small) | 回调实收 | 结果 |
|---|---|---|---|
| 20000, 10000 | 78, 39 | 78, 39 | PASS |
| 0, 40000 | 0, 156 | 0, 156 | PASS |
| 65535, 65535 | 255, 255 | 255, 255 | PASS |
| 0, 0 | 0, 0 | 0, 0 | PASS |

换算关系：`motor = round(xinput_ushort / 65535 * 255)`，误差 0。

### 4.2 端到端（真机）

接收端（便携版 exe）→ 手机在线 → 连续下发 6 组震动。手机侧
`dumpsys vibrator_manager` 的 `Recent vibrations` 新增**5 条**记录：

```
11-06 06:07:01.806 | effect | finished | duration: 73ms | usage: UNKNOWN | com.vgamepad
11-06 06:07:02.340 | effect | finished | duration: 72ms | usage: UNKNOWN | com.vgamepad
11-06 06:07:02.894 | effect | finished | duration: 73ms | usage: UNKNOWN | com.vgamepad
11-06 06:07:03.448 | effect | finished | duration: 77ms | usage: UNKNOWN | com.vgamepad
11-06 06:07:04.555 | effect | finished | duration: 75ms | usage: UNKNOWN | com.vgamepad
```

6 组下发只产生 5 次振动，差额是 `(0,0)` 那组——被
`handleRumble()` 的 `amp < 8` 门限正确抑制，属设计行为。

### 4.3 回归

注册力反馈后，22 项输入矩阵仍全部通过（除 A 键一项因贴屏幕顶边、
adb 注入易被系统手势截获，单独按压实测正常）。`update()` 延迟稳定在 0.04 ms 均值。

## 5. 手机端可调参数（已存在，无需改动）

| 设置项 | 键名 | 默认 | 作用 |
|---|---|---|---|
| 游戏震动回传 | `rumble` | 开 | 总开关 |
| 震动强度 | `rumble_gain` | 80% | 幅度增益，`amp * gain` |
| 震动时长 | `rumble_dur` | 24 | `dur = 30 + v*1.7` ms |
| 最小间隔 | `rumble_gap` | 32 | `gap = 30 + v*2.2` ms |

## 6. 已知边界

1. **只做单马达融合**：手机只有一个振动器，PC 下发的大/小马达按
   `max(large, small)` 取较大值，不做双马达分别驱动（硬件限制）。
2. **高频抑制**：游戏以 60 Hz 以上下发时，强度不变且未超最小间隔的请求会被
   手机端合并，避免持续振动耗电与手感糊成一片。
3. **未接手机时不发**：`receiver._rumble_addrs` 未登记目标地址则直接返回，
   不产生无效 UDP。
