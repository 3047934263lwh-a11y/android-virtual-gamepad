# 虚拟手柄 · 自动更新系统 使用与发布教程

> 零编程基础也能照着做。本教程覆盖：日常发新版本、手机端更新操作、常见问题排查、
> 把更新模块复用到其他 Android 项目、签名密钥保管。

---

## 一、这套系统是什么

手机上的「虚拟手柄」App 现在会自动：

1. **检测新版本**——每隔一段时间（12 小时）和手动点击「检查更新」时，向 GitHub
   询问有没有比当前更新的正式版；
2. **弹窗提示**——发现新版本时弹出中文更新窗口（当前版本 → 最新版本、安装包大小、
   更新日志），可以选择「暂不更新」或「立即更新」；
3. **自动下载**——点击「立即更新」后自动从 GitHub 下载安装包，显示百分比进度，
   支持**断点续传**（中断后重试会接着上次的位置继续下载）；
4. **安全校验**——下载完成后自动做 4 道检查，任何一道不过都**拒绝安装**：
   - SHA-256 与发布者公布的校验值一致（文件没被篡改、没下坏）；
   - 包名与当前应用一致（`com.vgamepad`）；
   - 新版本号必须高于当前版本；
   - 签名证书与当前应用一致（确认是同一开发者发布）；
5. **系统安装**——校验通过后自动调起 Android 系统安装界面，点「安装」完成
   **覆盖升级**。全程不需要卸载旧版本，**用户数据全部保留**。

任何一步失败（断网、下载失败、校验不过……）都只显示原因，**不影响已装软件正常使用**。

## 二、发布一个新版本（最常用流程）

前提：代码已推送到 GitHub 仓库 `3047934263lwh-a11y/android-virtual-gamepad` 的 main 分支。

### 第 1 步：改版本号

打开文件 `android/app/build.gradle`，找到：

```
versionCode 30
versionName "1.1.1"
```

- `versionCode`：整数，**每次发布必须 +1**（手机靠它判断新旧，绝不能倒退）；
- `versionName`：给人看的版本号，如 `"1.1.2"`。

### 第 2 步：提交并推送

把改动的文件全部同步到 GitHub main 分支（用你现有的同步方式即可）。

### 第 3 步：打标签发布

在 GitHub 网页上：仓库页 → **Releases** → **Draft a new release** →
**Choose a tag** → 输入新标签名（必须与 versionName 一致，如 `v1.1.2`，
注意带 `v` 且**不要**和已有标签重复）→ 填写更新日志（这段文字会显示在手机
更新弹窗里）→ 点 **Publish release**。

> 网页发布方式会创建空 Release，由 Actions 自动补构建 APK 和校验文件。
> 也可以用命令行方式：`git tag v1.1.2 && git push origin v1.1.2`（标签指向
> versionName 一致的提交）。

### 第 4 步：等待自动构建

推送标签后 GitHub Actions 自动执行：构建 APK → 计算 SHA-256 → 把两个文件
传到该 Release。大约 3–5 分钟，到仓库 **Actions** 页可看进度。

### 第 5 步：手机收到更新

手机上打开 App（或点设置里的「检查更新」）→ 弹出更新窗口 → 立即更新 →
下载完成自动校验 → 系统安装界面点「安装」→ 完成。

### 强制更新（可选，极慎用）

在 **Release 描述正文里**加入强制更新标记，弹窗会变为**不可关闭**、没有
「暂不更新」、点外部也关不掉——用户只能更新。仅在出现严重安全/数据问题、
旧版必须立刻淘汰时使用。标记的字面量见 `UpdateConfig.kt` 的 `FORCE_MARKER`。

> **只在这一处、且只在确实需要时写。** 下面这些地方**绝不能出现**该字面量：
> CI 的 Release 描述模板、开发说明、CHANGELOG、提交信息、PR 描述
> （`generate_release_notes` 会把提交信息带进 Release 描述）。
> 一旦误入，所有老版本用户都会被强制更新弹窗锁死——2026-11-08 已真实踩过一次。

## 三、手机端更新操作说明

1. 弹出「发现新版本」窗口后：
   - 点 **「暂不更新」**：窗口关闭，软件照常使用，12 小时内不会重复打扰；
   - 点 **「立即更新」**：开始下载，显示百分比与已下载大小；
2. 下载中可点 **「取消下载」**：已下载的部分会保留，下次「立即更新」从断点继续；
3. 下载完成自动校验（约 1–2 秒，无需操作）；
4. 第一次更新时系统会要求授权：
   - 弹出「需要安装权限」→ 点 **「去授权」** → 打开
     **「允许来自此来源的应用」**开关 → 返回 App，自动继续弹出安装界面；
   - 该授权只需开启一次，且只允许本应用安装自己的更新；
5. 系统安装界面点 **「安装」**→（部分手机会询问安全性）→「继续安装」→ 完成；
6. 升级后打开 App：连接记录、按键布局、所有设置**全部保留**。

## 四、常见问题排查（FAQ）

| 现象 | 原因与处理 |
| --- | --- |
| 「暂时无法检查更新」 | 手机当前无法访问 GitHub（api.github.com）。换个网络或稍后再试；不影响使用 |
| 「已是最新版本」 | 当前版本 ≥ 最新正式 Release。注意 Draft / Pre-release 不会被检测 |
| 下载很慢或失败 | GitHub 下载走海外 CDN，高峰期可能较慢。失败后点「重新下载」会从断点继续，不会从头下 |
| 「SHA-256 校验不一致」 | 下载文件损坏或被篡改。点「重新下载」；若反复出现，联系发布者核对校验文件 |
| 「签名证书不一致」 | 说明该安装包不是官方发布，**已自动阻止安装**，属于保护机制 |
| 「新版本号不高于当前版本」 | 发布者标错了 versionCode。不会安装 |
| 「手机存储空间不足」 | 清理存储后点「重新下载」 |
| 点了安装没反应 / 提示未知来源 | 设置 → 应用管理 → 虚拟手柄 → 允许「安装未知应用」 |
| 更新后设置丢失 | 正常情况下不会发生（覆盖安装保留数据）。若发生请反馈 |

## 五、复用到其他 Android 项目

更新模块在 `android/app/src/main/java/com/vgamepad/updater/`，共 3 个文件：

| 文件 | 作用 |
| --- | --- |
| `UpdateConfig.kt` | **唯一配置文件**：仓库 owner/name、检查间隔、超时等 |
| `UpdateEngine.kt` | 引擎层：Release 解析、版本比较、断点续传下载、四重安全校验 |
| `UpdateManager.kt` | 界面与编排：更新弹窗、下载进度、安装授权引导 |

复用步骤（约 10 分钟）：

1. 把 `updater/` 三个文件复制到新项目的源码目录；
2. 改 `UpdateConfig.kt` 里的 `REPO_OWNER` / `REPO_NAME`；
3. 新项目 Manifest 加：`REQUEST_INSTALL_PACKAGES` 权限 + FileProvider（照抄本
   项目 Manifest 与 `res/xml/file_paths.xml`）；
4. Activity 中：`private val updateManager by lazy { UpdateManager(this) }`，
   `onCreate` 里 `uiHandler.postDelayed({ updateManager.checkOnLaunch() }, 3500)`，
   `onResume` 里 `updateManager.onHostResume()`，设置页加一个
   `updateManager.manualCheck()` 按钮；
5. 新项目仓库配置 Secret `KEYSTORE_BASE64` / `KEYSTORE_PASSWORD` / `KEY_ALIAS` /
   `KEY_PASSWORD`（见第六节）+ 复制 `.github/workflows/release.yml`；
6. 注意：新项目的 APK 必须与「手机上已装的那个项目」同签名，否则更新会被
   签名校验拦截（这正是保护机制在起作用）。

## 六、签名密钥保管（重要）

### 现状：已从调试密钥换成正式密钥

| 版本 | 签名 | 说明 |
| --- | --- | --- |
| v1.1.0 及更早 | **Android Debug**（`CN=Android Debug`，SHA-256 `7659aefd…f91bfd02`） | 早期作品，用系统自动生成的调试密钥 |
| v1.1.1 | Release 上的 APK 是**正式证书** | 但该标签的 `build.gradle` **没有** `signingConfigs` 段——见下方警告 |
| v1.1.2 及以后 | **正式证书**（`CN=VirtualGamepad`，SHA-256 `23e9a21b…51f0435`） | 源码与发布资产一致 |

**正式密钥**：`vgamepad-release.keystore`（别名 `vgamepad`），**必须妥善备份**：

1. **备份**：存一份到安全位置（当前在 `C:\Users\30479\android-toolchain\`，
   另建议存网盘）。丢失 = 无法再发布「签名一致」的更新，只能卸载重装；
2. **GitHub 构建**：Actions Secret `KEYSTORE_BASE64` 存该密钥的 base64，
   `KEYSTORE_PASSWORD` / `KEY_ALIAS` / `KEY_PASSWORD` 存对应口令。CI 构建时
   解密注入，`build.gradle` 通过环境变量读取；Secret 加密存储，不进代码与日志；
3. **本地构建**：把口令写进 `android/keystore.properties`（已被 `.gitignore`
   排除，**严禁入库**）；
4. **v1.1.0 用户无法直接升级**：debug 签名与正式证书不同，覆盖安装会被系统
   拒绝（`INSTALL_FAILED_UPDATE_INCOMPATIBLE`），必须卸载重装一次，数据会清空。

### ⚠️ 禁止从 v1.1.1 及更早的标签重新发版

v1.1.1 那个标签的 `android/app/build.gradle` 里没有 `signingConfigs` 段，
AGP 会退回用 **debug 密钥**签名。用它重新构建，产出的 APK：

- 与 Release 上挂的那个（正式签名）不是同一把钥匙；
- 已装正式版的用户**装不上**（签名不一致被系统拒绝）。

因此 `release.yml` 现在有两道硬闸门，触发任一即中止发布：

1. **构建前**：检查 `build.gradle` 是否声明了 `signingConfigs.release`；
2. **构建后**：用 `apksigner` 实测 APK 证书指纹，不等于
   `23e9a21b…51f0435` 就拒绝上传 Release。

> 闸门只对「包含新 workflow 的提交」生效——v1.1.1 标签自带的是旧 workflow，
> 所以它**不会被自动拦住**。这条只能靠人守：**要发版就从 v1.1.2 及以后构建，
> 不要 checkout 老标签。** 老版本不需要重建，需要修就发新版本号。

## 七、发布前检查（每次打标签前过一遍）

| # | 检查项 | 不做的后果 |
| --- | --- | --- |
| 1 | `versionName` 与要打的标签一致 | CI 第一步就失败 |
| 2 | `build.gradle` 含 `signingConfigs.release` 且 release 引用了它 | CI 第二步失败 |
| 3 | 构建产物证书 = `23e9a21b…51f0435` | CI 构建后校验失败，拒绝发布 |
| 4 | **Release 描述里不得出现强制更新标记的字面量** | 弹窗不可关闭，老用户被卡死（见下方说明） |
| 5 | 提交信息、PR 描述同样别写那个字面量 | `generate_release_notes` 会把它带进描述 |

> 第 4、5 条是 2026-11-08 踩过的坑：CI 的 Release 描述模板里带了一句开发提示，
> 其中恰好含有强制更新标记，导致 v1.1.3 / v1.1.4 的描述都命中，
> 老版本用户一检查更新就会被不可关闭的弹窗锁住。模板已清除，别再写回去。
